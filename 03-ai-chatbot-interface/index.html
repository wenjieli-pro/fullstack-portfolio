Aether AI 2:14 PM

Found it — this is the classic reference identity in the dependency array trap. Your effect depends on user, but it also sets user. Every fetch produces a fresh object, which is a new reference, which re-triggers the effect. Infinite loop.

UserProfile.jsx 
// ✕ Bug: the effect re-runs because `user` is a new object each render
useEffect(() => {
  fetch("/api/users/" + userId)
    .then((res) => res.json())
    .then((data) => setUser(data));
}, [userId, user]);  // ⟵ new reference every render
 
// ✓ Fix: depend on primitives only, and cancel stale requests
useEffect(() => {
  const controller = new AbortController();
 
  fetch("/api/users/" + userId, { signal: controller.signal })
    .then((res) => res.json())
    .then(setUser)
    .catch((err) => if (err.name !== "AbortError") console.error(err));
 
  return () => controller.abort();
}, [userId]);

The key changes:

  • Removed user from the dependency array — it was never an input, only an output.
  • Added a cleanup function so in-flight requests are cancelled on unmount or when userId changes.
  • Ignored AbortError so cancelled fetches don't spam the console.

Aether AI 2:16 PM

Three habits cover almost every case I've seen in production MERN apps:

  • Depend on primitives. If you need an object, depend on its id and read the object inside the effect.
  • Always return cleanup. Any subscription, timer or fetch should be cancelled on the way out.
  • Derive, don't store. If a value can be computed from props or state, compute it during render instead of syncing it in an effect.
